[0] (Heading 2) REPORT PREPARATION GUIDELINES
[1] (Normal) These guidelines are provided to keep all individual PBL reports concise and consistent. They may be removed from the final submitted report after formatting and content checks are completed.
[2] (List Bullet) Page setup: Use A4 paper with 1-inch (2.54 cm) margins on all sides.
[3] (List Bullet) Font and headings: Use Times New Roman: 16 pt bold uppercase for main chapter headings, 14 pt bold for section/subsection headings, and 12 pt for body text. Use Courier New 10-11 pt for SQL/code.
[4] (List Bullet) Paragraph format: Use justified body text with 1.5 line spacing and consistent paragraph spacing. Avoid unnecessary blank lines.
[5] (List Bullet) Report structure: Follow the prescribed chapter sequence. Do not add unrelated chapters or repeat the same content in multiple sections.
[6] (List Bullet) Template cleanup: Replace all placeholders with project-specific content and remove instructional text, unused rows, unused acronyms, and empty placeholders before final submission.
[7] (List Bullet) Recommended length: Keep the main report concise, normally about 20-30 pages excluding appendices; use additional pages only when the project genuinely requires them.
[8] (List Bullet) Abstract and keywords: Write a 150-200 word abstract as one paragraph and provide 4-6 specific keywords. Do not include citations, figures, tables or code in the abstract.
[9] (List Bullet) Present a precise problem statement, measurable objectives, scope/assumptions, solution strategy, functional requirements and one final approved ER diagram.
[10] (List Bullet) Show the logical relational schema, keys and integrity constraints, important functional dependencies, normalization up to 3NF, data dictionary, representative DDL and sample data. Keep the complete SQL script in Appendix A.
[11] (List Bullet) Demonstrate how the Java/Python application uses the logical database design through database connectivity, module-to-table mapping, CRUD operations, business-rule validation, reports, application screens and test results.
[12] (List Bullet) ER diagram quality: Ensure the ER diagram is readable and consistent with the final relational schema. Entity names, keys, relationships and cardinalities should match the implemented design.
[13] (List Bullet) Tables: Number tables consecutively in order of first appearance and place the table number and title above each table, for example, “Table 3. Functional Requirements”.
[14] (List Bullet) Figures: Number figures consecutively in order of first appearance and place the figure number and caption below each figure, for example, “Figure 2. Login Screen”.
[15] (List Bullet) Cross-references: Refer to every table and figure in the main text before or near its first appearance. Update the List of Tables and List of Figures after captions are final.
[16] (List Bullet) Screenshots: Use clear, cropped and labelled screenshots showing only relevant application content. Include evidence of data entry, search/display, update or transaction processing, and at least one report/output.
[17] (List Bullet) Testing: Include meaningful positive and negative test cases. Expected and actual results should be specific, and the status should reflect the observed outcome.
[18] (List Bullet) References: Use IEEE style. Cite sources in the text using [n], number references in order of first appearance, and include only sources actually consulted and cited. Remove the illustrative reference examples before final submission.
[19] (List Bullet) Appendices: Place the complete database script, source-code/repository reference and supplementary outputs in the appendices rather than expanding the main report with lengthy code.
[20] (List Bullet) Final submission: Check spelling, numbering, page consistency, captions, lists, references and repository access. A suggested file name is RollNumber_Name_DBMS_PBL_Report.docx (and PDF if requested).
